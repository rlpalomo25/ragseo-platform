# Doc 208: Change Ripple Protocol

**Version:** 2.19 | **Last Updated:** August 5, 2026 | **Series:** 200 (Workflow & Governance) | **Full version history:** `RAGSEO Changelog.csv`

## Purpose

Whenever a doc changes, other docs, skill-drafts, and pipelines built on top of it can go stale without anyone noticing until a page fails audit or Karen catches it by reading. Today that happened three separate ways on the same change: Doc 153 dropped a real Doc 193 dependency without the registry noticing, Doc 316 drifted stale on facts Doc 114 had already corrected, and four different skill-drafts (mastershield-writer, ragseo-auditor, klean-gutter-writer, mmgg-writer) all carried the same missing rule independently, because a fix landing in a canon doc does not automatically reach the skill wrapper built from it. This doc is the checklist that catches that before it ships, not after.

## When to run this

Any time a doc in `company\ragseo\` is edited with a real content change (not a typo fix). Skip it for pure formatting or spelling corrections with no rule change.

## Before you ripple: bump the changed doc

Before running the ripple, update the doc you just changed so its own header doesn't lie: bump its **Version** and set **Last Updated** to today, and update that doc's row in the System Documentation Spreadsheet (`Version`, `Last Updated`). A doc whose body changed but whose header date didn't is invisible to the next person deciding what's current. Skip only for typo/formatting fixes with no rule change.

## Non-bypassable (added July 27, 2026, Karen)

These three rules answer the standing question: *how does every change actually force this protocol to run, and how does it come back with conflicts before things just get applied?* The prose steps below still describe the reasoning; these make it mechanical and non-optional.

**A. The changelog row is the trigger AND the mandatory artifact.** An edit to any `ragseo` doc is not "done" until its row exists in `RAGSEO Changelog.csv` with the **superseded string in the search-key column** (§2B). No row means the sweep has no input, which means the ripple cannot run — so the change is incomplete, not finished-pending-cleanup. Write the row as part of the edit, not after.

**B. The sweep is a command now, not a hopeful grep — run `tools/ripple_check.py`.** Steps 2 / 2B / 3C are mechanized. After logging the row, run it:
- `python3 tools/ripple_check.py --from-changelog 1` — sweeps the newest changelog row's search key(s) across every live doc.
- `python3 tools/ripple_check.py --old "old value" --new "new value"` — conflict scan: lists docs that still carry the old value (CONTRADICTS) vs. docs that carry both (MIXED, review).
- It excludes `RETIRED/`, `_archive/`, and the changelog index itself; it **includes** `skill-drafts`; it **exits non-zero while any live doc still carries the old language.** The ripple is not closed until it comes back clean or every remaining hit is an explicitly ruled exception (e.g., an author-bio "nine utility patents" that is correct by design). A reversal is only findable if its old language was logged as the search key (§2B) — the tool is only as good as that row.

**C. Surface conflicts before applying — never reconcile unilaterally.** When a change contradicts existing canon in another doc — the conflict scan returns a CONTRADICTS list, or you notice a fact clash while editing — **stop, report the conflict to Karen, and get a ruling before applying anything.** Do not silently pick a side, reconcile it yourself, or "apply stuff" and note it afterward. A direct instruction to make the change is not authorization to overwrite a conflicting canon fact without surfacing it first; the requester asking for the change does not waive the conflict check, exactly as a request for "the publish version" does not waive the Doc 328 audit. Applying first and flagging later is the specific failure this rule exists to stop. (This is how the feet/homes contradiction was handled correctly on July 27: found during the IPISC sweep, flagged to Karen, ruled shared, *then* applied — not reconciled on the spot.)

## Stale-Mount Verification (added July 29, 2026, Karen)

A different failure than Single Thread of Record, below: this one isn't about another session changing a file, it's about your own fresh read of a file silently coming back wrong anyway. Reported incident: a session pulling Doc 328 to continue work on recent changes got the same old content on the first two fetches — no error, no warning, just stale bytes served as if they were current. The session only caught it because a byte-for-byte diff against what it already had didn't match; it worked around it by copying the file to a new filename to force a fresh pull.

**What this is, plainly:** these canon docs live in a cloud-synced (OneDrive) folder mounted into each session's sandbox. There can be a caching layer between the actual file and what a given read returns, and in rare cases that cache can lag behind a very recent edit — worse right after the kind of same-day, same-file collision this doc already documents (two edits landing minutes apart, like the Doc 328 v16.4/v16.5 case). **This is not fixed by this entry, and can't be — it isn't a canon-rule problem, it's an infrastructure one.** What's added here is a detection habit and a known recovery step, so the next session that hits it has a playbook instead of discovering the workaround from scratch, the way this one had to.

**The habit:** before treating a pulled canon doc as ground truth for a high-stakes action (about to run an audit, about to do a large rewrite off it), don't trust a single read. Cross-check it a second way — read it again via a different path (e.g. `Read` tool vs. a `bash cat`/`md5sum` on the mount), or, if something already looks off (a version number that seems too old given what you know just changed), force a fresh pull the way this incident's session did: copy the file to a new filename on disk, then read the copy. If the two reads disagree, that's the stale-mount symptom, not a content conflict — don't attempt to reconcile it as if it were one.

**Verified directly this session:** re-pulled Doc 328 via both the `Read` tool and the bash mount side by side — identical content, identical byte count, v16.5 both times. Not reproducing here right now. That doesn't mean the reported incident didn't happen; it means this is intermittent/session-specific, not a standing guaranteed failure, and it's recorded honestly as such rather than either dismissed or oversold as fixed.

**Reproduced later the same engagement (added July 29, 2026, v2.15).** After writing five canon-doc edits (Doc 192, 328, 329, 208, the Changelog) directly to the device and getting a clean `device_commit_files` success on all five, a follow-up re-stage of the same paths came back with stale pre-edit content on **every one of the five files** — not just Doc 328. The tell: the tool's own result JSON reported the *correct* new `mtimeMs` and byte count each time, but the file content actually delivered at the staged path was still the old version (confirmed by diffing against the edited source and by `wc -c` disagreeing with the tool's own reported byte count). **The metadata is not proof of fresh content — only a byte-for-byte content check is.** Independent confirmation the underlying device file *was* actually correct: `device_list_dir` on the same folder reported the new, correct sizes for all five files throughout. So the staleness was local to the re-staged copy in this session's own mount, not the device or OneDrive side. **Recovery that worked, every time:** delete the locally-cached copy at the staged path first (`rm` it), then call `device_stage_files` again on the same device path — the fresh delete-then-restage consistently pulled the true current content. Simply re-staging again without deleting first did not help; it kept returning the same stale bytes with the same falsely-current-looking metadata.

## One Deliverable, No Orphaned Attempts (added July 29, 2026, Karen)

A third failure in this same family, but on the output side rather than the canon-doc side. Single Thread of Record is about another session changing a canon doc behind your back. Stale-Mount Verification is about your own read of a canon doc silently coming back wrong. This one is about the **deliverable page itself**: two files in `company/pages/` both looked like the finished version, and only one of them actually was.

**What happened, plainly:** while building AEGIS 5X v7.4 to close the gaps in Doc 192's new Publish-Readiness Manifest (visible JSON-LD, article archetype, meta title/description, single-document completeness), a second file — `... (v7.4 - Publish Package).html`, plus a matching PDF — ended up sitting in `company/pages/` alongside the real deliverable, `... (v7.4 - Doc 328 PASS WITH NOTES).html`. The real file was logged in the changelog, re-audited against the new checks, and referenced from the rolling handoff. The second file was none of those things — not logged, not audited, not mentioned anywhere in canon. It wasn't a harmless duplicate, either: its own internal changelog said it "converted all 4 JSON-LD blocks from hidden `<script>` tags to visible, copyable code blocks" — which on inspection meant it **deleted** all four functional `<script type="application/ld+json">` blocks rather than adding a visible copy next to them, exactly the mistake the Manifest fix exists to prevent. A publisher who grabbed that file instead of the real one would have shipped a page with zero machine-readable schema, silently undoing the day's whole fix. Its filename — "Publish Package" — also read as *more* finished and publish-ready than the correct file's name, not less.

**Root cause:** nothing anywhere said a delivered page must have exactly one candidate file in `company/pages/`, or that a superseded draft/attempt has to be moved out the moment it's replaced. Every other rule this doc tracks assumes you're looking at *a* file; nothing said to check whether you were looking at the *only* one.

**The fix:** Doc 192 v2.8 adds a Manifest line requiring exactly one delivered file per version, and states plainly that a more polished-sounding filename is not evidence of correctness. Doc 328 v16.10 and Doc 329 v1.19 gate it — a second candidate file for the same version is now a FAIL on sight, independent of whether the file being audited is itself fine. The orphaned file and its PDF were moved to `company/pages/_to_delete/`, not left in place.

**The habit, going forward:** before handing a page off, or before trusting a "final" file at all, glance at the folder it lives in — not just the file already open. If more than one file could plausibly be *the* deliverable for that version, stop and reconcile which one is real before doing anything else with it.

## Single Thread of Record (added July 28, 2026, Karen)

Karen's proposal, stated directly: keep all RAGSEO canon work — doc edits, skill reinstalls, page fixes — in one conversation, so nothing changes anyplace else. This is the correct instinct and is adopted as the working rule. Stated honestly, not oversold:

- **What this rule actually is:** a discipline, not a lock. Nothing in Cowork can prevent a different chat, a different agent, or Karen herself in a second window from opening and editing a file in `company\ragseo\`. The three real collisions logged this engagement (Doc 113 §5.10; Doc 328 v16.4/v16.5; this doc sitting at v2.11 with a real ripple_check.py already built, unrecorded in the rolling handoff doc until this edit) all happened *because* work landed outside the thread treating itself as the system of record.
- **What actually backstops it, since a promise isn't a gate:** (1) **re-read the live file's own header before trusting any cached number** — not the rolling handoff doc, not memory of an earlier turn in this same conversation, the file on disk, every time, before editing it. This is what caught the v2.10→2.11 gap just now. (2) `tools/ripple_check.py` (§ Non-bypassable, item B) — run it, don't just intend to. (3) The rolling handoff doc (`RAGSEO System State (Rolling Handoff).md`) is a snapshot for onboarding a new chat, explicitly labeled as going stale the moment work continues elsewhere — it is never the tiebreaker against a live file's own header.
- **The practical rule, going forward:** treat every other open or future RAGSEO-related conversation as a potential concurrent editor until proven otherwise, and check the header, not the memory of the last session, before every edit. If a genuine second thread of work is unavoidable (Karen working two chats at once, or a scheduled task firing mid-session), the collision-handling pattern already in use — bump forward, note the collision transparently, lose no content — is the fallback, not a failure.

## Consolidate, Don't Duplicate (Step 0 — added August 2, 2026, Karen)

**Run this before you write a single word of fix text, ahead of the four steps below.** The four steps make sure a fix reaches every doc that depends on it. This step makes sure that reach happens as a pointer, not a copy-paste — because the default failure mode this whole engagement keeps producing is a rule's full logic getting restated, verbatim or near-verbatim, in every doc that touches it, until a file is bulky with the same explanation three or four times over and Karen is the one who has to notice and say so.

1. **Grep for the substance, not the doc number, before deciding where a fix goes.** Search the full `ragseo` folder for the concept itself — the rule's own language, not just a doc citation — so you know every place it already lives before adding a new one.
2. **One doc owns the full explanation. Everyone else gets a pointer.** If the rule already has a canonical statement somewhere — a doctrine doc like Doc 144, Doc 194, or Doc 113 — that doc keeps the reasoning, the worked examples, the *why*. Every other doc that has to enforce or reference it gets a one-line pointer ("confirm X per Doc NNN") — never the full logic copied in again.
3. **No existing home yet → create exactly one.** Put the new rule in the single doctrine doc that most naturally owns it. Don't write it inline into every audit gate that will need to check it.
4. **Audit gates get the mechanic, not the doctrine.** Doc 328/329 checks need to be actionable on their own — what to list, what counts as a violation, what fails — so they will always restate that much. What they should not restate is the *why*: the reasoning, the worked example, the background. Keep the fail condition; point to the doctrine doc for the rest.
5. **Found it already stated in 2+ places? That's a finding, not a shrug.** If a fix in progress surfaces the same rule already written out in full in multiple docs, collapse it into one canonical statement plus pointers as part of the same pass — don't leave the existing duplicates standing and add a third.

**What this isn't:** a gate that restates its own fail condition in plain language is not a violation of this rule — that's the minimum a gate needs to be actionable without five other files open. The line is between the *mechanic* (stays, everywhere it's checked) and the *doctrine* (lives once, gets pointed to).

**Flagged, not yet done:** today's stacking-rule fix (Doc 144 v1.5, Doc 328 v16.30, Doc 329 v1.27) is exactly the pattern this step exists to stop — the full rule ended up written out in all three files rather than living once in Doc 144 with Doc 328/329 pointing to it. Left as-is for now rather than retroactively edited under this same message; flagged here as a concrete candidate for a future consolidation pass if Karen wants one.

## Changelog Hygiene — No Version History in the Doc Body (added August 5, 2026, Karen)

The same "Consolidate, Don't Duplicate" instinct above, applied to a different kind of bloat: not a rule restated in multiple docs, but a doc's own history piling up in the one place an executing agent has to read past to do its job. Karen, opening Doc 361-MS Instructions directly: "there is almost a page of versions at the top in prime real estate for needing to read before the agent does anything." Measured: 20 lines, roughly 4,000 tokens of pure history, read on every single run, before Step 0.

**The rule.** Any instructional or agent-facing doc — every Doc-XXX the pipeline, refresh, or audit agents load, and every skill draft — carries **no accumulated version history in its own body.** The header states only the current version, the last-updated date, and a pointer: `**Full version history:** RAGSEO Changelog.csv`. Full changelog narrative — what changed, why, root cause, who found it — lives in `RAGSEO Changelog.csv` (Document, Version, Date, Change, Superseded string), not restated in the doc.

**When this runs.** Every time a version bump touches one of these docs, as part of that same edit: write the new entry to `RAGSEO Changelog.csv` directly, do not add it to the doc body first and migrate later. If the doc still has old inline entries from before this rule, migrate all of them to the changelog CSV in the same pass — don't leave partial history sitting in both places.

**What this doesn't touch.** Short inline reasoning sitting *inside* a rule, next to the rule itself — e.g. a "(added August 4, 2026, Karen)" tag on a Doc 430 truth entry, or the Doug Allen exception note in Doc 100 §11.0 — is not a changelog entry, it's load-bearing context for a judgment call, and stays. The distinction: a top-of-file chronological list of every past version is pure history nobody needs to do the job; a one-line "why" sitting next to an active rule is part of doing the job. Doc content-page Appendices (a page draft's own "Not for Publish" revision notes) are a separate case, already handled — walled off from the reader-facing content and excluded from publish by convention, not sitting in the doc's own working real estate.

**Worked example, same day.** Doc 361-MS Instructions: 15 accumulated entries, 20 lines, ~4,000 tokens, migrated to `RAGSEO Changelog.csv`; doc body now carries one line. This doc (Doc 208) was itself the worst offender in the corpus at the time this rule was written — both a top-of-file blockquote stack (v2.8-2.18) and a second, separate bottom-of-file list (v1.0-2.4) — both migrated in the same pass that added this section, rather than exempting the doc that just wrote the rule.

## The four steps

**1. Check the System Documentation Spreadsheet's `Outputs To` column for the doc you just changed** (the master relationship index; the former Document Registry is retired 2026-07-18). Every doc listed there depends on it; open each one and confirm it still reflects the change.

**2. Grep the full `ragseo` folder (not just the registry) for literal citations of the doc's number.** The registry is hand-maintained and can itself be wrong or incomplete, Doc 153's own row didn't list its Doc 193 dependency until it was fixed this session, despite Doc 153 citing Doc 193 directly in its own text. A plain-text search catches what the table misses. Do this before trusting the Feeds Into list as complete.

**2B. Grep the CHANGED VALUE, not just the doc number. This is the step that catches what Step 2 cannot.** A doc can carry the thing you changed without ever citing the doc that owns it. When Doc 192 renamed the above-fold labels, a grep for "Doc 192" found the writers and the 361 set — and completely missed Doc 1710 and Doc 204, which never cite Doc 192 but both contained the literal string `Quick Answers`. They stayed stale and contradicted the new rule for weeks. **The doc number is not the search key. The changed string is.** Search by change class:

| Change class | What you grep for | Why Step 2 misses it |
|---|---|---|
| **Rename** (`Summary` → `Key Takeaways`) | the **old name**, case-insensitive, plus near-variants (`## Summary`, `Quick Answers`, `quick answers`) | docs use the label without citing its owner |
| **Renumber** (15 sections → 14) | the **old number** with its phrase (`"15 sections"`, `"15 standard"`) | the count is restated in checkers that don't cite the format doc |
| **Value change** (`0.0008%` → `0.00001%`) | the **old value** | stale figures hide in example lists, not in citations |
| **Retirement** (Doc 154 retired) | the **retired doc's number** — and check `RETIRED/` is excluded from your edit targets | live docs keep naming a dead enforcer; edits get wasted on retired files |
| **Reversal** (de-staged prose → `.qa` component) | the **superseded rule's language** (`"prose, not a staged"`) | **the hardest class — see below** |

**Reversals are the dangerous class, because they leave no shared string.** A rename leaves a trace you can search for. A reversal doesn't: the new rule (`.qa` component) and the old rule ("de-staged prose") have no word in common, so nothing links them and **nobody greps for the rule they just deleted.** That is exactly how Doc 1710 kept demanding flowing prose while Doc 328 failed pages for it. **When you reverse a rule, record the superseded language in the changelog spreadsheet as the search key** — that is what the changelog CSV is for: it is not just a record, it is the ripple search index for the next sweep.

**Scope:** search all `Doc *.md`, the 361 set, `skill-drafts`, and the CSVs. **Exclude `RETIRED/` and `_archive/`** — a hit there is not a finding, and editing one is wasted motion. **Also exclude the index itself** (this doc and `RAGSEO Changelog.csv`): they contain every search key by design, so they match every sweep. The index is not a finding.

**3D. Missing entirely is the same finding as stale — not an exemption.** When propagating a fix across a sibling set (the three main writers, the three 361 tracks, the three brand modules), check whether the rule is present in every sibling, not just whether the siblings that already carry it are now correct. A sibling that never had the rule at all causes the same downstream failure as a sibling with a stale copy of it, a reader following that sibling gets it wrong either way. **Do not defer a missing-entirely finding as "pre-existing, out of scope" just because your current change didn't cause the absence.** If the rule is supposed to exist there, its absence is a live ripple finding today, fix it in the same pass, or explicitly flag it to Karen as a finding needing her call, never silently note it and move on as if it weren't part of the sweep. (This takes Section 5's standing Check E — Sibling Parity — and makes it a rule for every reactive per-change ripple too, not just the occasional full sweep: don't wait for the monthly pass to catch a sibling that was simply never given the rule.) **Verification note:** confirm absence by reading the actual section, not by an empty search result — a citation/keyword grep in files-matched mode can return nothing because the sibling inherits the rule by a pointer phrase ("Identical to Doc 361-MS") that doesn't contain your search term, not because the content is missing. Read before declaring something absent.

**3B. No orphans.** Every doc must be associated with at least one other doc — a Feeds Into, a dependency, or a named consumer — recorded in the System Documentation Spreadsheet (the former Document Registry is retired). **An orphan is invisible to Step 1 and unreachable by a relationship-based ripple**, so it drifts silently until a page fails or Karen catches it by reading. When this protocol surfaces a doc that nothing points to and that points to nothing, that is itself a finding: register the relationship or retire the doc. A doc with no relationship has no owner, and a doc with no owner goes stale by default.

**3C. Fact changes → sweep the Fact-bearing set.** Doc 114 (Brand Fact Registry) is the **single source of truth** for brand facts — warranty rate (0.00001%), feet installed (10M+), homes (75,000+), patents (Karen 9 / portfolio 17+), ASTM B117-16, five shingle approvals. Those numbers get *copied* into many docs, so they go stale in scattered places. On any fact change: (1) update Doc 114 first; (2) in the System Documentation Spreadsheet, filter to every doc flagged **Fact-bearing (must match Doc 114)** and reconcile each; (3) record old→new value in the changelog CSV as a ripple search key (§2B) — a stale figure hides in example lists and correction notes, not in citations. Usual stragglers: the brand modules (130/131/132), the 361 Knowledge Packs, and Doc 900.

**3. Grep `skill-drafts` separately, and check by content, not just citation.** Skill-drafts often paraphrase a canon doc's rules into their own words rather than citing the doc number, so a citation grep alone will miss them. Check whether each skill-draft's own stated rules still match the doc you just changed. This is the layer that broke silently four times today; a skill-draft is a separate, cached artifact from the doc it was built from, and nothing keeps them in sync automatically.

**3E. Skills go stale faster than docs — the re-diff is mandatory, not a "check if you remember" step (added July 27, 2026, Karen).** For high-traffic doc/skill pairs — Doc 328 ↔ ragseo-auditor above all, plus Doc 316/320/324 ↔ their writer skill-drafts — every version bump of the doc requires re-reading the paired skill-draft line by line the same day, not a spot-check whenever someone happens to notice drift. Treat this the way a hard-gate check is treated, not an optional Step 3 pass: **the rule in force is whichever version of the doc is current on disk right now, never whatever the skill-draft last said**, and a skill-draft that hasn't been re-diffed since the doc's last bump is presumptively stale until checked, not presumptively fine. Where a skill-draft is found paraphrasing/curating content instead of pointing to the doc (e.g., a "Key gates" excerpt), flag that specific passage as a standing conversion candidate — replace the paraphrase with a live pointer where practical, don't just patch the wording again and leave the same drift-prone shape in place for the next bump.

**Also: verify a doc's self-description, don't just cite it (added July 27, 2026, Karen).** A doc that says "this now matches Doc X exactly" or "no longer diverges" is stating an intent, not a proven fact. Before repeating that claim to Karen, check it against a real built artifact on both sides, if one exists. If no finished artifact exists yet to test against, say so plainly — "the claim is untested doctrine, not verified practice" is a real, honest answer, and a better one than repeating the doc's own confidence back to her. Karen's own framing: the ripple protocol "doesn't always do a deep dive and get it all right," and that's a standing risk to name here, not something to quietly try to do better next time without saying so.

**4. Report a checked list, not a changed list.** For every doc and skill-draft the ripple search surfaced, state one of: confirmed current, no change needed; updated, with what changed; or flagged, needs Karen's input before touching. Do not report only the files you edited, list what you verified and found already correct too, so the check is auditable later.

This time the ripple check ran *while making the change*, not after a page shipped wrong or Karen caught it:

- Doc 192 itself: rewrote the Output Format and Required Block Order sections to retire the blue/black Google Doc build sheet in favor of the styled HTML + bottom Appendix.
- Doc 328 (auditor): rewrote Handoff Conformance (Section 0) and Paragraph Spacing (Section 4D) to check for the new format.

**A new failure pattern surfaced doing this, worth naming separately from plain staleness:** Doc 328 had a check, "De-staged prose above the fold: Fail if the above-fold Your Questions Answered block is formatted as a staged Q&A block." ## Section 5: The Full-System Consistency Sweep (standing pass, distinct from the per-change ripple above)

**Why this is a different tool, not a stronger version of the same one.** Steps 1-4 above are *reactive*: they trigger when a specific doc changes and trace that one change's blast radius. They catch drift from a single edit. They do **not** catch drift that accumulates silently across many separate edits over weeks — two docs that quietly disagree because each was edited correctly, in isolation, by a different session, with no single edit ever triggering a ripple between them. That's a structurally different failure, and it needs a pass that doesn't start from "what changed" but instead walks the *whole* library looking for places it disagrees with itself. This surfaced concretely on 2026-07-21: a third-party developer review of the 361 system found real, live contradictions (a CTA mismatch between Doc 324 and Doc 132; an FAQ word-count rule in Doc 328 that contradicted Doc 316/320/324) that had sat unnoticed for days because nothing had ever swept the system for internal disagreement, only for the effect of one specific change at a time.

**What it checks (mechanical, not judgment — a script does this, not a manual read):**

| Check | What it catches | Real example found 2026-07-21 |
|---|---|---|
| **A. Reference resolution** | Every "Doc ###" citation actually points to a file that exists | Several docs cite numbers (Doc 200, 223, 226, 301, 341-344, 436, 450) with no matching file — likely never-built roadmap docs or typos, not urgent but real |
| **B. Retired-but-cited** | A live doc still points at something that only exists under RETIRED/ | Doc 208 itself, Doc 900, Doc 193, and 3 others still cite Doc 154 and Doc 133, both retired |
| **C. Orphan docs** | A doc that neither cites anything nor is cited by anything — invisible to the relationship-based ripple in Step 1 | None found this run — a good sign the registry has been kept current |
| **D. Header/mtime mismatch** | A doc's own "Last Updated" header lags its real edit date — the exact failure Doc 208's own "bump the header" instruction exists to prevent | 20+ docs found with headers weeks-to-months stale, including two from **this session's own edits** (Doc 123, Doc 174) — fixed on the spot |
| **E. Sibling parity** | For known sibling groups (the three 361 tracks, the three main writers, the three brand modules), does a required marker/rule appear in **all** of them, not just the one that was being worked on that day | Confirmed clean this run — the KB standing-file requirement, the entity-bind pointer, and the Restricted Claims embed all landed across all three siblings correctly |
| **F. Verbatim duplication** | The same long paragraph copied into two or more different docs instead of one owning it and the rest pointing to it — every copy is a future contradiction waiting to happen | Found: identical "Bullet arc" doctrine copy-pasted across 5 separate playbooks instead of living once in Doc 155; two live, differently-versioned copies of Doc 260 and Doc 263 sitting side by side |

**Where the tool lives:** `company/ragseo/tools/system_consistency_audit.py` (staged in the outputs folder as of 2026-07-21, pending your confirmation to save it into the canonical folder). It's read-only — it never edits anything, only reports. Findings still require judgment: Check A in particular throws false positives on things that look like citations but aren't (a range like "Doc 130-132" meaning "Docs 130 through 132," not a literal doc numbered "130-132"). Read every finding before acting on it; don't auto-fix off the report.

**Cadence — an event trigger, not a calendar, per Doc 207's own precedent ("a gate, not a calendar"):**
1. **Before any external handoff** (a file manifest to a developer, a package to a third party) — this is the one that would have caught yesterday's issues before they reached him.
2. **At the end of any session where 5 or more docs were edited** — the threshold at which accumulated changes are likely to have drifted apart from each other.
3. **A monthly floor regardless** — so slow drift between active sessions still gets caught even if neither trigger above fires.

**Ownership:** I (the agent) run this and report findings the same way Step 4 already requires — a checked list, not just a changed list: what was fixed, what's flagged for your judgment, and what's noted but not urgent. You are never expected to run the script yourself or know what a "citation" or an "orphan doc" means; that's the whole point of building it into this protocol instead of asking you to learn the mechanics.
