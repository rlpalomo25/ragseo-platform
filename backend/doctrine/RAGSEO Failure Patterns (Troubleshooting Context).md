# RAGSEO Failure Patterns — Troubleshooting Context

**Purpose:** this is not the Rolling Handoff. The Rolling Handoff (`RAGSEO System State (Rolling Handoff).md`) is for "what's the current state, what's open, what do I do next." This doc is for "something just broke somewhere — in a live page, in Robert's agent output, in a skill run — and I want to know if it's a known shape before treating it as brand new." Bring this doc into a fresh task when that happens. A new session should read this before diagnosing anything, the same way it reads the Rolling Handoff before doing anything.

**What goes in here, and what doesn't:** this file tracks *recurring failure patterns* — structural reasons this system breaks, not the day-to-day list of what got asked or fixed. A page that shipped with a wrong stat and got corrected doesn't belong here once it's fixed with no residual mechanism behind it. A gate that let that wrong stat through unchecked, or a fix that didn't propagate to the doc's siblings, does — because that mechanism can produce a *different* wrong stat next time. Test before adding something: if this exact bug is gone but the shape of it could recur wearing a different face, it's a pattern. If it's just closed, it isn't.

**The three shapes to check first.** Nearly everything logged below is one of three things:

- **A: Documents/systems out of sync with each other.** Two things that are supposed to agree — a doc and its paired skill, a rule and its gate check, two files both claiming to be the same deliverable, a citation and the thing it cites — quietly stop agreeing, and nothing forces them back into alignment.
- **B: Something that worked repeatedly, then silently stopped.** A check, a habit, or a process ran correctly for a while — sometimes a long while — and then degraded or got skipped, with no error, no notice, nothing that announced the change. By the time it's noticed, it's usually noticed by its output (a bad page, a missing report), not by the failure itself.
- **C: Logic stops flowing between documents (added July 30, 2026, Karen).** Different from A — nothing is technically out of sync, no version numbers disagree — but the *reasoning chain* has a broken or missing link. A rule is defined upstream (what a brand's argument should do, what a page should verify) and something downstream that's supposed to check or execute that reasoning never actually does, or checks a label standing in for the logic instead of the logic itself. The paperwork can look perfectly consistent while the actual thinking has a gap in it.

When something breaks elsewhere, start by asking which of these three shapes it looks like. That alone usually narrows it to 2-3 candidate patterns below.

## Category A: Out of sync

**A1 — Skill draft vs. installed skill.** A Cowork skill is a *frozen copy* of the doc(s) it executes, made at `save_shot` / `save_skill` time. Editing the draft file changes nothing until the skill is explicitly reinstalled. Found engagement-wide: all six original skills sat frozen at their last-install date (mostly July 12) while their source docs kept moving — weeks of silent drift. *Mitigation:* `ragseo-daily-skill-resync` (scheduled task, ~6am daily) now hash-checks every skill's draft against its last-synced state and reinstalls only what actually changed, logging to `skill-resync-state.csv` / `ripple-log.csv`. *Residual risk:* only covers the skills and doc pairings it already knows about (see §3 pairing table in the Rolling Handoff) — a brand-new doc-skill pairing, or a skill drifting for a reason *other* than its paired doc changing, still needs a human or an in-session agent to notice.

**A2 — Ripple failures: a fix in one doc doesn't reach its siblings.** The system has real dependency chains (Doc 114 facts → Doc 316/320/324 writers; Doc 328 checks ↔ Doc 329 checks; a doc's own citation of another doc's version). A fix landing in one link doesn't propagate automatically. Concrete instances: Doc 153 dropped a real Doc 193 dependency without the registry noticing; Doc 316 drifted stale on facts Doc 114 had already corrected; four skill-drafts independently carried the same missing rule; Doc 329's C2 trademark fix didn't reach Doc 328's identical check for weeks. *Mitigation:* `tools/ripple_check.py --from-changelog N`, driven by the Changelog's "superseded string" column, now runs as a mechanized sweep (daily, and by discipline on every doc edit) instead of a manual eyeball scan. *Residual risk:* the tool is only as good as the changelog row — if an edit ships without logging its old/new language in the superseded-string column, the sweep has nothing to search for and will not catch it. Treat "no changelog row" itself as the first thing to check when a ripple is suspected.

**A3 — Hardcoded version citations go stale.** A doc names another doc's version inline in prose ("per Doc 192 v2.2") instead of just naming the doc. The cited doc moves on; the citation doesn't. Found: all three Doc 361 Instructions docs cited "Doc 192 v2.2" after Doc 192 had moved to v2.6 — caught only because Karen asked directly whether 361-track output would match a same-morning stylesheet change. *Pattern to watch for:* any prose citation that includes a version number is a future staleness bug waiting to happen; a reference to a doc *name* alone doesn't have this problem. When troubleshooting a doc that "seems to be following an old rule," check its own citations for a baked-in version number before assuming the rule itself is wrong.

**A4 — Parallel-session drift (Single Thread of Record).** Two sessions edit the same canon docs without either knowing about the other. Not just theoretical — reproduced live twice: Doc 208 itself was found at v2.11 when the Rolling Handoff still recorded v2.10 (a real section had landed in an untracked parallel session); a Doc 328 v16.4/v16.5 version-number collision happened the same way. *Mitigation:* Doc 208's "Single Thread of Record" rule — keep canon work in one conversation — is a discipline, not a lock; nothing technical stops a second session. *How to recognize a live instance:* a doc's actual on-disk header doesn't match what any handoff/context doc says it should be. Always re-read the live header before trusting a recorded version number, including in this file and the Rolling Handoff.

**A5 — Orphaned duplicate deliverable files.** Two files in `company/pages/` both look like "the" finished version of a page, and only one is real. Found July 29: an undocumented `AEGIS 5X ... (v7.4 - Publish Package).html` sat next to the real, audited, changelog-logged `... (v7.4 - Doc 328 PASS WITH NOTES).html` — the orphan had actually *deleted* all four functional JSON-LD `<script>` blocks while adding a human-visible copy, so a publisher grabbing it instead of the real file would have shipped a page with zero machine-readable schema. The orphan's name read as more finished, not less. *Mitigation:* Doc 192 v2.8 / Doc 328 v16.10 / Doc 329 v1.19 — exactly one candidate delivered file per version is now a gated check, FAIL if a second exists regardless of which one is in hand. *How to recognize a live instance:* before trusting any "final" file, glance at the folder it lives in, not just the file already open — check `company/pages/` for a second file with the same base name/version.

**A6 — Either/or scope gaps between rules that individually look complete.** Two rules each cover part of a space, written as though the parts don't overlap, and a real page falls in the gap between them. Found twice on the same rainwater-harvesting page: (1) Doc 361's Step 5 called its own inline writer checklist "the audit gate," leaving no clear line to the *actual* gate (Doc 329) — KG/MMGG siblings already named it correctly, MS didn't; (2) the Ask This/Six-Questions framework was treated everywhere downstream as a substitute owed only to non-guardian pages, while the gate checks (Doc 329 C10, Doc 328 §7D) only required it on comparison/buying pages — a guardian-anchored, non-comparison page satisfied neither trigger and got the block nowhere. *How to recognize a live instance:* a page or case that is arguably "neither" or "both" of two categories a rule set assumes are mutually exclusive and exhaustive. Ask directly: does every real page type map to exactly one branch of this rule, or could something fall between?

**A7 — A canon file can't be written through the normal path, and the real reason isn't what it first looks like.** `Doc 135_ Brand Argument Architecture.md` returned repeated write failures on July 29 (generic permission errors via the device-bridge bash/Edit path), which read like "the file is probably open in another app." On July 30, Karen uploaded the file directly into the chat instead, which let it be read and edited with no problem — but writing the edited copy *back* to the same live device path still failed, this time with a specific, different error: **Windows denied the write because of Controlled Folder Access (ransomware protection)**, not a generic app-open lock. Every other canon doc in the same folder wrote successfully all day, so this isn't a folder-wide block — something specific to this file or this write attempt tripped it. *How to recognize a live instance:* a write failure that names Controlled Folder Access explicitly (rather than a bare permission-denied) means the fix is on Karen's machine, in Windows Security → Ransomware protection → Allow an app through Controlled folder access — not something retriable from this session. *Working technique either way:* uploading the file directly into the chat reliably gets around a read-side lock/permission problem (it bypasses the device-bridge read path entirely), even when it doesn't guarantee the write-back will succeed too — treat "have Karen attach the file" as the first move for any canon doc that won't stage or edit normally, and confirm separately whether the write-back needs her to change a local setting first.

## Category C: Logic stops flowing between documents

**C1 — A rule's underlying logic is defined but never actually verified, only a label standing in for it is.** Doc 135 defines a real, specific argument structure per brand — Argument Posture, Claim Hierarchy (e.g., MasterShield: Mechanism → Engineering Proof → Durability Outcome → Homeowner Benefit) — that's supposed to shape how every page actually argues its case. As of today, Doc 328/329 verify that a page's `article_archetype` *label* is present and matches the plan (Rule 1a, added July 30) — but nothing anywhere checks that the page's actual paragraph-by-paragraph argument sequence follows its brand's defined Claim Hierarchy. A page could carry a perfectly correct archetype stamp while arguing in the wrong order for its brand, and no gate would catch it. This is the difference between checking that a form was filled out and checking that what's on the form is true. **Open, not yet fixed** — flagging it here is itself the first step; whether to add a real Claim-Hierarchy-conformance check to Doc 328/329, and how an auditor agent would even verify argument sequence rather than just presence/absence, needs a decision, not just a doc edit.

**C2 — The two production tracks can silently diverge on what they each require for the same brand and page type.** The lean Doc 361 refresh track and the full Doc 153→316/320/324→328→192 pipeline are supposed to produce consistent, complementary results for the same brand — a page refreshed via 361 shouldn't read like it came from a different rulebook than one built through the full pipeline. They've drifted at least once already: the Ask This/Six-Questions requirement (Doc 142 §11B) was scoped one way in the writer docs (316/320/324) and Doc 361's Instructions independently, and neither matched what the gate checks (Doc 329 C10, Doc 328 §7D) actually enforced, until all of them were reconciled July 29 (see A6). *How to recognize a live instance:* any time a rule gets added or changed on one track (e.g., a Doc 316 fix) without the same session checking whether the matching Doc 361 Instructions/Knowledge doc needs the identical fix, and vice versa. Ask directly, for any new rule: does this apply to both tracks, and does each track's doc actually say so, not just the doc you were looking at when you fixed it?

**C3 — A doc's own internal cross-references don't resolve to one unambiguous thing.** Smaller than the others, but a real logic gap: Doc 135 runs two independent "Rule 1/2/3" numbering schemes in the same document — one in its own Quick Reference summary (homeowner-first / stable-variable / no-repeat-archetype) and one in Section 5 (Archetype Rotation / Stable-Variable / Information Density) — and they don't map 1-to-1 (Quick Reference's Rule 3 is Section 5's Rule 1). Anyone citing "Doc 135 Rule 2" without also naming a section could mean either of two different things. Found while adding Rule 1a (July 30) and deliberately not fixed in the same pass, to avoid silently renumbering every existing cross-reference to Doc 135's rules without Karen's sign-off. *How to recognize a live instance elsewhere:* any doc that numbers things more than once (a summary box and a body section, say) is a candidate — check whether the numbers actually mean the same rule in both places before trusting a citation that only gives a number.

## The System Architect Lens

Karen's framing: a system-architect/manager role holds constant awareness of the *whole* system and how its parts engage each other — not just whichever doc or page is in front of them. Four things that role would track continuously:

**1. The artifact chain, and which doc governs each stage.** A page moves through four distinct artifacts, not three — the fourth is easy to forget because it doesn't ship to the reader:

| Stage | Artifact | Governing doc(s) | Where it lives |
|---|---|---|---|
| 1. Plan | Execution Plan (brief) | Doc 153 (+ Doc 193 format) | `execution-plans/` |
| 2. Write | Drafted page, per brand (×3: MasterShield, Klean Gutter, MMGG) | Doc 316 / 320 / 324 (full pipeline) or Doc 361-MS/KG/MMGG (lean refresh) | `company/pages/` (draft stage) |
| 3. Audit | Gate report — pass/fail with evidence | Doc 328 (full pipeline) or Doc 329 (lean refresh) | `company/audits/` |
| 4. Publish | Handoff document — the one self-contained file with everything needed to go live | Doc 192 (format) + Doc 260 (WordPress transfer steps) | `company/pages/` (delivered stage) |

The audit stage is the one most likely to go missing silently (see B1/B2) precisely because it doesn't produce anything the reader ever sees — a page can visually look complete without it.

**2. The two tracks, and the obligation that they agree.** The lean 361 refresh and the full pipeline are two different paths to the same kind of output, and Karen's standard is that they present consistent, complementary results — not two rulebooks that happen to share brand names. Every rule change should be asked: does this apply on both tracks, and did I actually update both, or just the one I was looking at? (See C2.)

**3. The parallel copies of canon that can drift independently of any single page.** Beyond the four-stage chain above, canon itself exists in more than one place at once: the live docs in `company/ragseo/`, the Cowork skills built from them (frozen at `save_skill` time, A1), and Robert's externally-fed Knowledge Packs (no resync mechanism at all, B5). A system architect checks not just "is this page right" but "which copy of canon produced this page, and is that copy current" — three different answers are possible for what should be one canon.

**4. Logic, not just version numbers.** Everything in Categories A and B is about things staying *synchronized* — same version, same content, same file. Category C is a different question: even when everything is perfectly in sync, does the *reasoning* still hold together end to end? Doc 135 defines how each brand is supposed to argue; nothing yet confirms a delivered page actually argues that way (C1). This is the newest and least-covered lens — worth a standing question on any new page or any new rule: not just "does this match the doc," but "does the doc's own logic actually show up in the output."

**What's likely still missing from this list:** a live cross-brand consistency check (Doc 135 §7's Structure Reuse Rule requires all three brands share the same Win Vector/structure/mechanism, but the tool meant to verify sentence-level non-duplication across brands has already come back unreliable once — flagged BLOCKED on the AEGIS 5X audit, only a manual spot-check as a substitute); and a standing view of which pages exist in *which* format generation at once (pre-July-10 build-sheet vs. Doc 192 HTML vs. whatever comes after) so that "is this page current-format" doesn't have to be rediscovered page-by-page the way it was for HydroVortex.

## Category B: Worked repeatedly, then silently stopped

**B1 — Self-audit mistaken for the real gate.** A writer's own inline checklist/self-audit table gets treated — by a doc, a person, or an agent — as equivalent to running Doc 328/329, when it was only ever meant as the writer's own sanity check. This is *the* recurring cause of pages shipping unaudited while looking audited. Doc 329 has said outright since it was written that a self-audit table "is not this," but that framing wasn't in Doc 328 itself (the main gate) until Karen forced the point (v16.2), and Doc 361-MS's Step 5 called its own checklist "the audit gate" until July 29. *How to recognize a live instance:* a page has a checklist that looks like it passed something, but ask specifically — was Doc 328 or Doc 329 actually *re-run* against this exact draft, producing a saved report in `company/audits/`? If the answer is "there's a checklist on the page saying it's fine," that is not evidence.

**B2 — "Final / ready to publish" claimed with no saved gate report.** The single clearest symptom of B1: a page is self-labeled "FINAL COPY — READY TO PUBLISH" (or equivalent) and no Doc 328/329 report exists for its exact slug/version in `company/audits/`. Found on `mastershield-rainwater-harvesting-FINAL.md` — every defect on it was something an existing gate check already would have caught, had the gate actually run. *Mitigation:* Doc 329 C17 / Doc 328's Non-Bypassable Trigger — a "final" label without a matching saved report is now treated as false on its face, not deferred to. *How to recognize a live instance:* the label is not the evidence. The saved report is. This applies just as much to Robert's external agent output as to anything built in Cowork — there's still no automatic resync keeping his agent current (see B5), so treat anything from that pipeline as needing its own report check, not an assumption of freshness.

**B3 — A daily/scheduled process silently degrades instead of failing loud.** `ragseo-daily-skill-resync` and its ripple sweep run unattended every morning. The failure mode to watch for isn't the task not running (that's visible) — it's the task running "clean" while quietly missing something it should have caught. Already happened once: a routine run found Doc 329 v1.14 and Doc 361-KG/MMGG changes with no paired skill of their own, correctly matched it to an already-known limitation, and chose not to surface it — a reasonable call *that time*, but exactly the kind of judgment call that can go wrong silently in a way a failed task never would. *How to recognize a live instance:* check `ripple-log.csv` not just for "did it run" but for what it decided *not* to escalate, especially after several clean runs in a row — a string of "nothing to report" is worth spot-checking the way a sudden failure wouldn't need to be.

**B4 — Stale-mount / cache serving old bytes (sometimes with metadata that lies too).** A fresh read of a canon doc silently returns old content, no error thrown. Reproduced twice this engagement: once reported as a same-day collision risk (Doc 328 v16.4/v16.5); reproduced live on July 29 while verifying a batch of five edits — every one of the five re-staged as stale content, and the tool's own reported metadata (`mtimeMs`/byte count) *also* showed the new, correct values while the actual bytes served were still old. `device_list_dir` on the same folder confirmed the real device files were correct throughout, so the staleness was local to the read-side cache, not the source. *Fix that worked:* delete the locally-cached copy, then re-stage — re-staging alone without deleting did not help. *How to recognize a live instance:* a version number that looks implausibly old given what you know just changed is the tell — don't trust a single read, and don't trust a tool's reported size/mtime as proof either; diff actual content two ways before treating either as ground truth for a high-stakes action (an audit, a big rewrite).

**B5 — No resync mechanism on the outside of Cowork.** Robert's external agent(s) producing 361-track pages are fed file snapshots manually — there is no equivalent of `ragseo-daily-skill-resync` keeping his side current. This is a standing, unsolved gap, not a one-off: Doc 329's C17 provenance check is a partial mitigation (it can catch a stale stamp *after* the fact, if the writer bothered to stamp it), but nothing stops an out-of-date agent from producing a page in the first place. *How to recognize a live instance:* any 361-track page from outside Cowork should be treated as an unknown-freshness input by default — check its provenance stamp against the live doc headers before trusting its content, the same way you'd check for a stale citation (A3).

## Quick triage, in order

1. **Which shape is this — A, B, or C?** (out-of-sync / worked-then-stopped / logic gap)
2. **Re-read the live file's own header directly** — don't trust a handoff doc, a changelog table, or a skill's memory of a version number. If you can, cross-check two ways (Read tool vs. bash, or a second stage after deleting the local cache) before treating a version number as fact — see B4.
3. **Check for a second candidate file** in whatever folder the "finished" thing lives in — see A5.
4. **Check the changelog for a row, and the row for a superseded-string** — no row means no ripple coverage — see A2.
5. **Check for a saved gate report, not a checklist on the page** — see B1/B2.
6. **Check whether a rule was written as either/or** and whether the current case is the gap between the two branches — see A6/C2.
7. **Check which copy of canon actually produced this** — live docs, a Cowork skill snapshot, or Robert's Knowledge Packs — before assuming the live doc's rules are the ones that applied. See A1/B5 and the System Architect Lens.
8. **Ask whether the underlying logic actually shows up in the output**, not just whether a label/version/checklist says it should — see Category C.
9. If none of the above match, it's probably a genuinely new pattern — solve it, then add it here before moving on, in the same terse, dated, "what it looks like / root cause / fix / residual risk" shape as the entries above.

## Maintenance of this doc

Keep this short and pattern-level, not a log. When a specific bug is fully closed with no mechanism left behind that could recur in a different form, don't add it here — or prune it out if it's already here and has been superseded by a real gate (e.g., once a pattern has a hard gate check and hasn't resurfaced in a while, consider whether the entry can shrink to one line rather than its full worked example). When a *new* structural pattern is found, add it in the same shape: what it looks like from the outside, the root cause, where it's been seen, the current safeguard if any, and — most importantly — how to recognize a fresh instance that doesn't look exactly like the last one.
